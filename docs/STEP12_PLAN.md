# Step 12 工程化加固计划(参考设计)

> 本文件是 Step 12 的设计参考:每项的现状、问题、改法、验收。
> **执行范围以对话里分批发送的指令为准**:只做当前这一批指令里列出的子步骤,不要提前做后续批次;本文件和指令不一致时,以指令为准,并在汇报里指出不一致的地方。

## 原则

这轮叫"Step 12 工程化加固":不加新功能,只把已有的简单实现做到"真要上线会怎么做"的程度。五条规则:

1. **只改已有的东西**。每一项都能指到一个现在已经存在的文件或机制,比如"重试已经有,但不分错误类型"。不做多轮对话、不加写工具、不换框架。
2. **不动 Agent 的分析行为**。优先加固"模型之外"的工程层(重试、幂等、连接、退出、可观测、权限),这些改动不影响模型的输出,不会把之前的分数改坏。会改变模型行为的项目(口径合并、澄清)单独放在 P1,且必须是开关、默认关闭。
3. **冻结的成绩不动**。holdout 93.94% 属于 Step 9 的代码,不重跑、不重新计分;README 和简历里继续这样写。加固后只跑 dev 回归,证明"没改坏"。
4. **每项都要有证据**。工程层的改动用测试证明(单元测试、故障注入、压测),不用调真实模型;结果和以前一样放进 `evidence/`,文档里的每个数字能对到收据。面试时说"加了熔断",要能接着说"故障测试里连续 5 次 503 后切到备用路径,耗时从 X 降到 Y"。
5. **保留前后对比**。每项都先写一个能复现旧问题的测试(在旧代码上失败),再改代码让它通过。这样面试时能讲清"原来会出什么事、现在怎么样"。

优先级的定义:**P0** 工程层、不影响模型输出、面试最常问,先做;**P1** 涉及安全或会改变行为,排在 P0 之后;**P2** 规模变大才需要,只写设计、不写代码。

## 逐项方案

每项四段:**现状**(代码里现在怎么写的)、**问题**(真上线会出什么事)、**改法**(具体到文件和参数)、**验收**(用什么测试和数据证明)。

### A. Agent 运行时

#### A1 模型调用的重试与熔断

**现状**:`agent/model.py` 的 `request()` 对任何异常都重试,最多 4 次,间隔 1/2/4 秒;SDK 自带重试关掉了(`max_retries=0`),单次超时 60 秒。

**问题**:

- 400(参数错、上下文超长)和 401 重试也不会好,白等 7 秒。
- 没有抖动:供应商一抖,所有 worker 在同一时刻一起重试。
- 不读 `Retry-After`,429 时按自己的节奏打。
- 供应商宕机时,每个任务都要把 4 次重试耗完才失败,既慢又给供应商增压。

**改法**:

1. 加错误分类函数:可重试(408、429、500/502/503/504、超时、连接断开)、直接失败(400/401/403/404/422)、上下文超长(400 且错误信息是长度超限,直接以 `context_limit` 终止)。
2. 退避改成全抖动:第 n 次等 random(0, min(上限, 1s × 2^n));有 `Retry-After` 就按它(秒数或 HTTP 日期),但不超过上限;所有重试的总等待时间不超过任务剩余时长。
3. 熔断器:状态要在所有任务间共享,但 Agent 子进程没有数据库权限。所以放在可信的 worker 侧:每次模型调用前已有一次预扣额度的控制回调(`CONTROL`),顺带查 `provider_health` 表(新迁移 010);处于打开状态就拒绝,子进程以 `provider_unavailable` 快速终止。worker 根据 `model_call` 事件里的错误更新计数;连续 5 次可重试错误打开,冷却 30 秒后放一个请求试探。阈值先用这个预设值,不调参。
4. `model_call` 事件增加 `error_class`、实际等待时间;终止原因拆成 `model_fatal`、`provider_unavailable`、`model_error`。

**验收**:用假的模型客户端做单元测试:400 只调 1 次;429 + `Retry-After: 2` 约等 2 秒;固定随机种子验证抖动范围;连续 503 后熔断打开,之后的任务在 100ms 内失败,冷却后半开放行一个。故障注入收据:用模型替身模拟供应商持续 503,比较改前改后 10 个任务的总耗时和对供应商的请求次数。

#### A2 无进展检测

**现状**:`agent/loop.py` 只在"同一工具 + 同一参数 JSON"连续出现 3 次时终止。

**问题**:三种兜圈抓不到:A-B-A-B 交替;SQL 只差空格或大小写;换参数兜圈(查 SP 空、查 RJ 空、查 MG 空…)。现在靠 20 步和 10 万 token 兜底,但那时已经花了很多钱。

**改法**:

1. SQL 先用 sqlglot 解析再生成标准写法,用它做签名,空格和大小写差异不再算"不同调用"。
2. 滑动窗口:最近 6 轮里不同签名不超过 2 种,判为交替循环。
3. 进展定义:连续 4 轮的工具结果全是错误或空结果、且没有产生新的 `result_id`,判为无进展。
4. 终止原因新增 `no_progress`,事件里记录触发的是哪条规则。

阈值(6 轮、4 轮)不凭感觉定:用已有的 97 次最终配置运行日志回放,要求零误判(正常任务步数最大只有 6)。

**验收**:单元测试构造三种兜圈轨迹,各自在第几步被拦下;日志回放报告"97 次运行、误判 0 次";最后一起跑一次 dev 回归(见第 4 节)。

#### A3 工具调用幂等

**现状**:每次 `run_sql` 都新插一行 `query_results`;MCP 客户端不重试;单 Agent 任务中断后整个重跑。

**问题**:只读工具重复执行结果不会错,但会重复存结果、重复打数据库;而且没有幂等就不敢给 MCP 调用加重试。将来一旦加写工具,这是必须的。

**改法**:两层。

1. 传输层幂等:Agent 每次调工具带 `Idempotency-Key = task_id + tool_call_id`;MCP 新增 `tool_calls` 表(主键就是这个 key,状态 running/done,对应的 `result_id`)。重复请求:done 直接返回原结果;running 返回"正在执行",客户端稍后重试。有了这一层,MCP 客户端才加 1 次连接失败重试。
2. 内容层去重:同一任务、同一条标准化后的 SQL、同一个 `data_version`,直接复用已有的 `result_id`,不再执行。这样任务重跑时,已经查过的 SQL 不会再打数据库。用唯一索引保证并发时也只有一份。

**验收**:同一 key 请求两次只有一行结果;两个相同请求并发只执行一次;重做一次"杀 worker 再恢复"的演示,对比改前改后重复 SQL 的执行次数。

#### A4 结果截断显式化

**现状**:`mcp_olist/sql_guard.py` 在没写 LIMIT 或 LIMIT 超过 1000 时改成 1000;返回里有 `row_count` 和 `row_limit`,但没说是否被截断。

**问题**:模型可能把前 1000 行当成全部,甚至对它做汇总;没有 ORDER BY 时,截掉的是哪 1000 行完全随机。之前的记录里也提到过"模型可能误以为分页能取到截断后的全量"。

**改法**:改成取 1001 行来判断:超过 1000 就只保留 1000 行并标 `truncated: true`,存进 `query_results` 的新字段;被截断且没有 ORDER BY 时加一句警告"无序截断,不代表前 N 名,汇总请在 SQL 里做";证据页也显示截断标记。

**验收**:单元测试覆盖三种边界:恰好 1000 行不算截断、1001 行算截断、自己写 LIMIT 500 不算截断。这一项会改变工具返回的文字,要包含在 dev 回归里。

### B. 服务与部署

#### B1 连接池与优雅退出

**现状**:API、MCP、worker 每次操作都 `psycopg.connect()` 新建连接(一次 `run_sql` 就要开两个);worker 是 `while True` 循环,不处理 SIGTERM。

**问题**:

- 每次建连接要走 TCP + 认证,并发高时既慢又会把数据库连接数打满;短连接还会产生大量 TIME\_WAIT。
- 发版重启 worker 时,正在跑的任务要等 30 秒租约过期才能被接管,而且这次中断还占掉一次"最多领取 3 次"的机会。

**改法**:

1. 用 `psycopg_pool.ConnectionPool`:API 一个池;MCP 两个池(agent 库、只读业务库分开);池大小、取连接超时(5 秒,取不到返回 503)、连接最大存活时间写进配置;取出时检查连接是否还活着(数据库重启后自动替换坏连接)。
2. 一个要讲清楚的细节:连接会被不同请求复用,所以超时、search\_path 这些设置必须是事务级的 `SET LOCAL`,不能是会话级的 `SET`,否则会泄漏给下一个请求。现在代码已经是 `SET LOCAL`,加一个测试防止以后改坏。
3. worker 优雅退出:收到 SIGTERM 后不再领新任务;当前任务给 20 秒宽限(小于 Compose 的 `stop_grace_period`);没跑完就杀子进程、立刻释放租约、把任务放回队列,并把这次主动释放记为 `released`,不扣"领取次数"。
4. 健康检查:API 和 MCP 加 `/healthz`(进程活着)和 `/readyz`(数据库可连、池未耗尽);worker 定期写心跳时间;Compose 配上 healthcheck。启动时校验必填配置,缺了就拒绝启动。

**验收**:压测下连接数峰值不超过池上限;重启数据库后服务自动恢复(B4 里做);任务进行中 `docker compose stop worker`,对比改前改后"任务被另一个 worker 接管的等待时间"(预期从最多 30 秒降到几秒)。

#### B2 全局限流

**现状**:只有每用户同时 2 个任务和每日额度;供应商限流靠遇到 429 再重试。

**问题**:用户多了以后,总请求量会超过供应商的 RPM/TPM,大量 429 之后再重试,是让供应商替我们限流。

**改法**:没有 Redis,就用 PostgreSQL 做共享令牌桶:`rate_buckets` 表存每个供应商的剩余令牌和上次补充时间,一条 `UPDATE ... RETURNING` 里完成"按时间补充 + 扣减"。扣减放在已有的预扣回调里,按预估 token 扣 TPM、按 1 扣 RPM;不够就等待(有上限),超时则让任务稍后重试。限额从供应商文档填入配置。

**验收**:单元测试验证补充计算;用模型替身(超过阈值就返回 429)跑 20 个并发任务,对比改前改后的 429 次数和实际 TPM。

#### B3 可观测:追踪、指标、成本

**现状**:只有 `events` 表;不同进程的耗时串不起来;没填单价,金额留空;没统计缓存命中。

**问题**:用户说"这次很慢",分不清是排队、模型还是 SQL 慢;没有指标就没法告警;不知道钱花在哪。

**改法**:

1. **追踪**:接 OpenTelemetry,一个任务一条 trace,span 包括创建任务、排队、worker 领取、每一步循环、每次模型调用(带 `gen_ai.*` 属性:模型名、输入输出 token)、每次工具调用、MCP 里的 SQL 执行。trace 上下文要跨进程传:API 存进任务行 → worker 传给子进程 → 子进程在 MCP 请求头里带 `traceparent`。Compose 加一个可选的 Jaeger。
2. **指标**:暴露 `/metrics`:任务数(按状态和终止原因)、模型调用数(按错误类型)、token(输入/缓存命中/输出)、模型和 SQL 和任务的耗时分布、队列积压、熔断状态、租约接管次数、闸门替换次数。告警阈值用参数文档里的分布(比如步数 p95 4、token p95 20,648)。
3. **成本**:配置里填输入、缓存命中、输出三种单价,每次调用按 usage 算金额,汇总到任务;如果供应商 usage 里有缓存命中字段,就统计命中率。

**验收**:一个真实任务生成一条从 API 到 MCP 的完整 trace(导出 JSON 和截图放进 evidence);`/metrics` 能采集;dev 回归时顺带算出每题平均金额和缓存命中率。

#### B4 故障注入与压测补全

**现状**:测过向量服务宕机、MCP 进程被杀、429(模型替身)、两个 worker 跑 6 个任务。

**问题**:没测数据库宕机和更高并发,"能承受多少任务"答不上来。

**改法**:新增场景,每个都先写预期行为:

- 任务进行中重启数据库:API、MCP、worker 自动恢复,任务重跑或失败但租约释放。
- MCP 和数据库之间加延迟和丢包(用 toxiproxy):超时按预期触发。
- worker 收到 SIGTERM:任务被快速接管(B1)。
- 供应商持续 503:熔断打开(A1)。
- 容量压测:用响应很快的模型替身,去掉模型耗时和费用,只测系统自己;比如 4 个 worker、100 个任务、200 个 SSE 连接,测吞吐、排队等待 p95、数据库连接峰值和错误数。

**验收**:每个场景一份收据:预期、实际、恢复时间;压测报告写清楚"替身模型下的系统容量",不冒充真实模型的吞吐。

### C. 安全、数据与行为(P1)

#### C1 MCP 按任务签发短期凭证

**现状**:所有请求共用一个静态 `MCP_BEARER_TOKEN`;任务 ID 和租约靠请求头 `X-Task-ID`、`X-Lease-Token`;黑板写入的角色是请求参数。

**问题**:拿到这个 token 的人能以任意任务的身份调用;Analyst 可以自称 reviewer 去写审核结论。

**改法**:worker(可信方)每次领取任务时,用单独的密钥签一个短期 JWT:`sub`=用户、`task_id`、`lease_token`、允许的角色、`aud`=mcp-olist、过期时间 = 任务截止时间。子进程只拿这个 token;多智能体每个角色一个 token。MCP 从 token 里取任务、用户、角色,不再信请求头和请求参数。静态 token 只留给健康检查。

**验收**:任务 A 的 token 读不到任务 B 的结果;过期 token 被拒;analyst token 写 review 字段返回 403;伪造的 `X-Task-ID` 被忽略。

#### C2 数据权限(行级安全)

**现状**:所有用户共用 `agent_ro`,能看全量数据。

**问题**:真实企业里区域经理只能看自己负责的区域;只靠提示词"不要查别的州"挡不住。

**改法**:用户增加数据范围(比如可见的州,默认全部)。在客户表和订单表上开 PostgreSQL RLS,策略读事务级变量 `app.allowed_states`;MCP 在每次查询事务里用 `SET LOCAL` 把 C1 token 里的范围写进去。要说明两个细节:模型写的 SQL 改不了这个变量,因为 AST 白名单只放行 SELECT 且 `set_config` 不在函数白名单里;查询了无权限的州时,要返回"无权限"而不是 0,不然又变成"没有数据当成零"。

**验收**:只能看 SP 的用户查 RJ,拿到明确的无权限提示;开 RLS 前后的 SQL 耗时对比;评测用户默认全部可见,不影响已有分数。

#### C3 日志与用户数据治理

**现状**:密钥已脱敏;事件里的问题原文没脱敏;没有保留期;用户只能删偏好。

**改法**:写入事件前用规则脱敏手机号、邮箱、证件号;定时任务按配置的天数清理旧的事件和查询结果(evidence 不动);用户删除接口级联删除任务、事件、结果、偏好、结论,并留一条删除审计。

**验收**:脱敏、过期清理、级联删除各有测试。

#### C4 上下文硬限制

**现状**:模型返回 usage 后才比较上限,超限那次已经计费。

**改法**:发送前预估输入 token:用历史日志里"字符数 → 真实 prompt\_tokens"的比例标定一个偏保守的系数;预估超限时先自动 mask 一次,仍超就在发送前终止(`context_limit_preflight`)。

**验收**:报告预估误差的分布(用已有日志);测试验证超限请求不会发出。

#### C5 数据版本与状态版本

**现状**:`data_version` 是 9 个导入文件的哈希,绕过导入脚本直接改库发现不了;黑板状态没有结构版本号,代码升级后旧断点可能读不了。

**改法**:业务表加语句级触发器,任何写入都给一个变更计数加 1,`data_version` = 导入哈希 + 变更计数;黑板状态加 `schema_version`,读到旧版本时走迁移函数,迁不了就放弃断点、整个重跑。

**验收**:手工 UPDATE 一行订单后,历史结论被降级为线索;用旧版本的黑板样例恢复任务。

#### C6 备用模型降级

**改法**:A1 的熔断打开时,切到配置的 `FALLBACK_MODEL`;切换前清掉上一个模型专有的字段(比如 `reasoning_content`);任务记录最终是哪个模型回答的。前提是备用模型先跑过一遍 dev,成绩写进文档;需要第二个供应商的 key,没有就跳过。

#### C7 口径合并与缺参澄清(会改变行为)

**现状**:"当前问题 > 偏好 > 知识库"只写在注入的说明文字里;缺时间范围时模型不一定澄清,是边界题的已知失败。

**改法**:把关键口径做成结构化槽位(销售额含不含运费、订单状态范围、客户按人还是按订单、时间范围),由代码按优先级合并后再交给模型;两个来源冲突或时间范围缺失时,直接返回澄清问题。开关 `SLOT_RESOLUTION`,默认关闭。

**验收**:和 Step 11 一样,跑前先写好采用条件(比如 C 17/17、E 6/6、D 不低于 6/8、边界题至少 8/10),只跑一次,达不到就保持关闭。这是上次失败的同一类问题,这次换成"代码判断"而不是"加提示词",结果好坏都是面试素材。

### D. 只写设计的部分(P2)

这些在当前规模下做了也测不出效果,只在 `docs/` 里写一页设计,面试时能讲清楚即可:

- **RAG 增量更新**:按文档和块的哈希判断增删改;先建新版本索引,建完再切换指针,避免更新中途查到新旧混合的数据。
- **RAG 元数据和重排**:知识库变大后加版本、生效日期、可见范围,先过滤再检索;召回 top-20 再重排到 top-3。
- **模型路由**:偏好抽取等简单任务换小模型,用已有的抽取评测集验证。
- **MCP 新规范迁移**:2026-07-28 版去掉了 initialize 和会话;项目已经是无状态 + 显式任务身份,迁移主要是客户端去掉 `initialize`、改用 `_meta` 带版本,等 SDK 支持后再做。
